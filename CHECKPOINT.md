## CP002 — текущее состояние

### Исправление после первой попытки раунда A

Повторный раунд A на коммите 2641198: пользователь сообщил два timeout на Intel.
Точные JSON-отчёты этих попыток не получены, поэтому этап таймаута клиента неизвестен.
Агент проверил local-arm64: оба процесса listener активны, контроллер включён,
адрес перепроверен; после READY channel=7 ни одного callback подключения не было.
Listener остановлен агентом перед сменой ролей. Следующий шаг — раунд B:
пользователь запускает listen на Intel, сообщает READY channel и адрес контроллера;
агент запускает connect на ARM64. Не повторять раунд A без новых данных.

- Пользователь сообщил peer-intel: status=failed, sha256_verified=false,
  reason=TypeError. Полный traceback на Intel не получен.
- local-arm64 действительно принял входящее подключение; старый listener
  завершился с receive:TypeError, SHA-256 не проверен, сервис удалён (status=0).
  Это подтверждает открытие канала, но не успешный обмен.
- Изолированный вызов реального ObjC -> Python callback показал: указатель
  данных приходит как int; срез data[:length] вызывает TypeError.
  Исправлено копированием через ctypes.string_at внутри callback с проверкой длины.
  Собственного C-кода нет.
- Исправлена независимая ошибка: openComplete на listener тоже отправлял REQUEST.
  Теперь REQUEST отправляет только connect, listener отвечает ACK после проверки.
- tools/rfcomm_bridge_test.py проверяет настоящий native callback на локальном
  буфере: PASS, pointer type=int. Self-test парсера и compileall также проходят.
- Добавлены error_message и error_frames без Bluetooth-адресов для следующих ошибок.
- Исправление пока проверено локально, повторный обмен с Intel ещё нужен.

Пользователь согласовал диагностический spike. Создан tools/rfcomm_probe.py:
listen/connect, фиксированный блок 4096 байт, SHA-256 ACK, таймаут supervisor,
временный SDP-сервис и отдельные JSON-отчёты. Инструкция: docs/CP002.md.

Проверено агентом на local-arm64 2026-11-16:

- self-test: фрагментация request/ACK, повреждённые и избыточные данные — PASS.
- compileall — без ошибок.
- Первый запуск выявил TypeError в объявлении selector PyObjC; точный traceback
  показал требование передать function. Исправлено, повторный запуск успешен.
- Listener: READY channel=7, ожидание 5 секунд, ожидаемый timeout без клиента;
  service_removal_status=0. Подключение и callbacks данных пока не проверены.

На peer-intel CP002 ещё не запускался. Следующий шаг: раунд A по docs/CP002.md,
затем раунд B. Не считать CP002 завершённым до результатов обеих машин.

## Как продолжить

1. Прочитать README.md, этот файл и инструкцию своей машины.
2. Проверить `git status` и `git log -3 --oneline`.
3. Сопоставлять отчёты по revision, dirty, machine и времени UTC.
4. Обновлять этот файл после значимого этапа: факты, препятствия и следующий шаг
   отдельно для каждой машины. Этап фиксировать коммитом, контрольный этап — тегом.
5. Наличие API и powered_on не считать доказательством работы соединения.

## История препятствий

Первоначальные попытки установки PyObjC и создания GitHub-репозитория в ограниченном
shell не прошли: DNS/сеть и запись .git были недоступны. Повтор с расширенными
разрешениями решил обе задачи. Первоначальный system_profiler не получил сведения
о контроллере; прямой вызов IOBluetooth теперь подтвердил его наличие.
