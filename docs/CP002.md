# CP002 — диагностический RFCOMM без OBEX

Это временный прототип, не программа передачи файлов. Передаётся фиксированный
блок 4096 байт. Listener проверяет содержимое и SHA-256, возвращает подтверждение;
connect проверяет подтверждение. Данные пользователей не читаются.

Роли можно менять независимо от архитектуры. Нужны близко расположенные Mac,
включённый Bluetooth и установленные requirements.txt. Если macOS запросит
сопряжение или разрешение, пользователь обрабатывает диалог на своём Mac.

## Раунд A: local-arm64 принимает, peer-intel подключается

Агент на текущем Mac:

```sh
.venv/bin/python tools/rfcomm_probe.py listen --machine local-arm64 --timeout 600
```

Дождаться `READY channel=N`. Канал может отличаться от запрошенного, если занят.
Агент сообщает фактический канал и Bluetooth-адрес отдельно в чате, не в Git.

Пользователь на Intel Mac:

```sh
git pull --ff-only
.venv/bin/python tools/rfcomm_probe.py connect --machine peer-intel --address AA:BB:CC:DD:EE:FF --channel 7 --timeout 60
```

Заменить адрес и канал значениями из чата. Адрес принадлежит listener, не клиенту.
Если окно 600 секунд истекло, агент перезапускает listener перед следующей попыткой.

## Раунд B: peer-intel принимает, local-arm64 подключается

Пользователь на Intel Mac:

```sh
.venv/bin/python tools/rfcomm_probe.py listen --machine peer-intel --timeout 600
```

В другом окне Terminal узнать локальный Bluetooth-адрес:

```sh
.venv/bin/python -c 'import IOBluetooth as B; print(B.IOBluetoothHostController.defaultController().addressAsString())'
```

Сообщить агенту адрес и канал из `READY`. Агент подключается с текущего Mac:

```sh
.venv/bin/python tools/rfcomm_probe.py connect --machine local-arm64 --address AA:BB:CC:DD:EE:FF --channel 7 --timeout 60
```

## Результаты

На обеих сторонах нужны `status: passed` и `sha256_verified: true`.
Для listener `passed` означает проверку блока и завершение отправки ACK;
только успешный connect подтверждает получение ACK второй стороной.
Один успешный listener не доказывает завершение всего обмена.

Отчёт пишется в `reports/cp002-<machine>-<role>-<time>.json`.
Прислать JSON либо снимок вывода `RESULT`. Сырой адрес в отчёт не включается.
Фиксируются revision и dirty: результаты разных версий не смешивать.

`timeout` без подключавшегося второго Mac — ожидаемый результат проверки запуска.
При ошибке сообщить reason, worker_returncode и этап последней строки вывода.
Код возврата 1 означает незавершённый/неуспешный тест.
При Ctrl-C или зависании системного API supervisor завершает worker;
временный SDP-сервис обычно удаляется macOS при выходе процесса. При штатном
завершении отдельно записывается service_removal_status (0 — успех).

Проверка парсера без Bluetooth:

```sh
.venv/bin/python tools/rfcomm_probe.py self-test
```

Реализация опирается на IOBluetooth API и описание SDP-словаря из заголовков
Apple SDK: IOBluetoothSDPServiceRecord.h и IOBluetoothSDPDataElement.h.
Ссылки: [PyObjC IOBluetooth](https://pyobjc.readthedocs.io/en/latest/apinotes/IOBluetooth.html),
[Apple: разработка Bluetooth-приложений](https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/Bluetooth/BT_Develop_BT_Apps/BT_Develop_BT_Apps.html).
